# 《从 0 搭建 AI Agent》写作规范

状态：长期约束，v1.0

## 1. 适用范围与优先级

本规范适用于 `book/src/` 的正文、章节新增内容、审阅意见和代码讲解。它是本书写作的唯一完整事实源；Agent 入口文件只引用它，不复制全文。

写作判断的优先级是：

```text
当前任务的明确要求
> 作者最新明确要求
> 作者稳定的人工写作模式
> 本规范
> 一般技术写作规范
> 模型默认文风
```

作者已有正文如果技术正确、上下文自然、信息完整且有个人节奏，不因“更正式”“更统一”而改写。除非任务明确要求，不把正文改成通用 AI 技术文章、Reference 或产品宣传文案。

## 2. 作者声音

把作者想象成真正实现过 Agent Harness 的工程师，带着另一名开发者从一个可复现的问题走到一个可运行的增量。读者应感觉有人在解释设计、试错和取舍，而不是模型在按大纲补齐章节。

可观察的语言特征：

- 现代技术语言为骨，文白相济；长短句交替，短句用于判断和收束，长句承载完整的因果和边界。
- 设问、反问、对偶、比喻和少量古意表达可以使用，但必须服务于当前技术问题。
- 信息密度高，却不省略为什么、前提、失败路径、边界和中间推理。
- 有明确工程判断，同时把事实、推断和本书的选择分开。
- 不用抽象口号掩盖技术缺口；技术先立住，文字再生花。

## 3. 章节推进

默认采用问题驱动，而不是术语驱动：

```text
上一版留下的真实问题
→ 直觉与具体例子
→ 最小模型、图或伪代码
→ 可运行代码增量
→ 运行结果与验证
→ 当前限制
→ 下一问题
```

每章最好对应一个可观察能力增量。正文应明确回答：上一版哪里不够、为什么现在需要这个抽象、本章增加了什么、新版本能做什么、仍然做不到什么。复杂抽象必须有产生它的历史；不能为未来需求提前造 interface、factory、middleware 或 plugin 层。

代码讲解以“问题 → 接口 → 关键代码 → 运行 → 观察”为主。每段代码都要说明为什么出现，以及运行后系统发生了什么变化。完整实现过长时正文展示关键部分，仓库承担完整代码；正文状态不得超过仓库实际验证结果。

图承担认知任务：数据流用数据流图，调用顺序用时序图，状态变化用状态图，算法用流程图或伪代码。能用 Mermaid、ASCII 或语言无关伪代码讲清楚时，先不要让具体语言打断第一次理解。

## 4. 句子与段落

不要把简洁变成省略。删除重复结论、空泛过渡和凑结构的段落；保留因果、前提、边界、反例和失败情况。不要用“显然”“不难发现”“自然可以得到”等词跳过困难推理。

短句可以形成节奏，例如“模型给出了答案。问题却没有结束。”但不要整页切成同长度短句。复杂技术边界允许使用结构清楚的长句，判断标准是读者能否一次读清主语、动作、条件和结论。

不要强行让每章都有“概述—原理—实现—优势—总结”，也不要让每章标题、段落长度和结尾完全相同。章节可以分别偏向 hands-on、解释或系统设计，但必须仍像同一作者。

## 5. 术语、引用与事实

第一次出现术语时可用“Agent Harness（Agent 运行框架）”或“Context Engineering（上下文工程）”，之后保持主要叫法，不在 Harness、编排框架、运行框架、代理执行层之间轮换。术语一致性优先于避免重复。

事实、推断和本书选择必须分开：

- 事实有官方文档、源码、论文或可复现实验支持；
- 推断用“从这个行为来看”“这意味着”“可以推测”等标记；
- 设计选择明确写“在本书中，我们选择”“这一版先”“当前实现暂时”。

允许引用 Dijkstra、Brooks、Ousterhout、Lamport 等经典人物和著作，但引用必须准确，并立即说明它解决了当前什么问题。不能确认逐字来源时不要加引号；删除引用后技术论证仍应独立成立。不要为了补文采随机插入名言。

## 6. 需要主动审查的 AI 模式

删除空洞开场，如“随着人工智能技术的快速发展”。谨慎使用机械“首先、其次、最后”、人为三段分类和连续总结。警惕无依据的“强大、先进、高效、完善、全面、至关重要、显著提升”，以及“统一规划、灵活调度、高效执行”式 PPT 四字词堆叠。

具体检查：

- 本章是否从工程问题进入，是否接住上一章留下的问题；
- 是否真的增加可观察能力，而非只增加术语；
- 是否把设计骨架写成已实现能力；
- 是否重复同一结论两三次；
- 是否用抽象句替代具体事实；
- 是否过度列表化、模板化，像 Reference、设计文档或产品说明；
- 是否有应画图的数据流、时序或状态变化；
- 是否存在过平的说明书语气，或过艳到干扰技术的修辞。

## 7. 状态与审阅

沿用仓库的状态词：`已实现并验证`、`P0 参考实现`、`设计骨架/尚未实现`。状态词必须与源码、测试和实际运行结果一致。

逐章审阅时按以下顺序判断：

```text
技术准确 → 教程逻辑 → 信息密度 → 作者一致性 → 文采
```

问题分级：

- **P0**：技术错误、因果断裂、代码与正文不一致、不可运行或前后矛盾；
- **P1**：明显风格漂移、AI 套话、模板化结构、正文像 Reference/设计文档；
- **P2**：局部紧缩、节奏、图示或引用机会。

默认先报告再改。只有明显 typo、语病、少量套话和文档引用关系可直接修复；不得在风格审查中大规模重写成熟正文。
