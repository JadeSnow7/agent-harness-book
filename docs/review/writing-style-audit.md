# 全书写作风格审查

日期：2026-08-08
范围：`book/src/SUMMARY.md` 中的全部正文与附录（ch0–ch16、阅读指南、实现索引、M2 实验）
依据：`docs/writing/style-guide.md`，并以 ch0–ch4 作为主要人工风格样本

## 1. Style DNA

这本书不是从术语表开始，而是从一个开发者已经撞上的问题开始。作者通常先把责任边界和失败情况摆出来，再用一个小例子、数据流或状态草图建立直觉；等读者知道“为什么现在需要它”，才引入接口和代码。代码不是 API 清单，而是一次可观察的系统增量：读者应看到请求如何变化、动作如何进入 Runtime、结果如何回来，以及这一版仍然不能保证什么。

语言上，作者以现代工程术语为骨架，偶尔用设问、短句和略带古意的转折调整节奏，但不靠修辞制造深度。成熟正文会明确区分模型声明与环境事实、确定性参考实现与生产能力、事实与本书的工程选择。它可以有判断和文气，却不应像宣传稿、论文摘要或 Reference。

判断一段文字是否像作者，关键不是句子是否足够短，而是：问题是否具体，因果是否完整，抽象是否由前面的失败逼出，代码是否回答“为什么”，结尾是否留下下一层真实问题。

## 4. 问题清单

### P0：技术或教学逻辑问题

本轮未发现可以仅凭正文审查确认的 P0。ch5–ch16 明确标记为设计骨架，正文没有把它们伪装成已实现能力；P0 参考实现的限制也反复交代。后续真正实现这些章节时，必须逐项核对代码、测试、验证命令和章节状态，尤其是 ch5、ch7、ch8、ch11、ch12、ch16。

### P1：明显风格漂移 / AI 味

1. **ch5–ch16 共享同一份设计骨架模板。** “学习目标 → 代码增量与验证 → 当前 P0 参考组合 → 验证场景 → 本章将得到什么”重复出现，使后半部像自动生成的章节卡片，而不是作者带读者完成一次工程推演。
2. **验证场景常被说两次。** 例如 ch5、ch6、ch10、ch15 先在段落中描述测试，再用“验证场景：”重复一遍。建议后续保留一次，并把另一处换成实际输入、事件或运行结果。
3. **“完成 Mx 后，系统将拥有……；这仍不等于……”成为固定结尾。** 这种诚实的限制说明应保留，但句式不必每章相同；可改为下一章真正接手的具体问题。
4. **后半部列表和接口草图多，具体动作少。** ch10、ch13、ch14、ch15 尤其明显，读者知道规则，却较少看到一个调用如何穿过边界。
5. **ch15 是最明显的 Reference 漂移点。** MCP、Skill、Hook、Plugin 的四项并列和安全能力清单信息正确，但当前连续案例不够，像术语整理而非问题驱动章节。
6. **ch16 的验收段落有报告腔。** “最终验收路径”和“最终验证场景”相邻，且都要求运行同一组检查，结尾可收束为一个具体的“哪些已证明、哪些仍待证明”的对照。
7. **中英文术语密度在后半部升高。** `durable recovery`、`progress oracle`、`delegation contract`、`capability manifest` 等词有必要，但首次出现时应始终让中文动作先成立，避免术语成为段落主语。

### P2：可进一步提升

1. ch6 可加入一个“预算不够时保留什么、丢掉什么”的最小输入输出例子；这是比抽象排序更容易记住的认知任务。
2. ch7/ch8 适合补一张带 sequence 的事件时序图；当前文字和代码草图需要读者自行拼接。
3. ch9/ch10 可共用一个 ChangeSet，从生成、审批到拒绝执行完整走一遍，减少两章各自重复约束。
4. ch12 的 `event_count=11` 和 `evidence_count=1` 适合作为事实证据，但应链接到实际运行命令或 fixture，而不是只作为数字出现。
5. ch13 可用“重复读取同一文件”展示 fingerprint 何时有用、何时不能直接判定失败。
6. ch14 可用一个父 Run 只接收子 Run 摘要的具体 JSON，体现“隔离”而不只是声明隔离。
7. 目前没有适合强行加入名人引文的位置。ch9 的 abstraction cost、ch13 的复杂度控制未来可能有引用机会，但应先有可靠原文来源。

## 5. AI 味热点

最明显的是 **ch5–ch6、ch10–ch15**，其中 ch15 最突出。热点不是空洞开场（全书基本没有），而是结构性模式：每章都先给状态和学习目标，再给一个 Rust enum 或流程图，再列验证场景，最后用“完成后拥有 X，但仍不等于 Y”收束。这个模式本身有教学价值，问题在于密度过高、缺少运行中的人类判断和局部节奏变化。

成熟的 ch0–ch4 则更多使用同一个 `hello.txt` 案例，具体说明请求怎么变、`call_id` 如何流转、Fake Transport 证明什么，所以读者感觉是在跟着实现走。后续章节应优先恢复这种“一个问题、一条状态变化、一项验证”的颗粒度，而不是统一套章节模板。

## 6. 下一步改稿顺序

1. **技术问题**：实现或冻结 M3–M10 时，先核对章节状态、伪代码、Rust/Python 源码、fixture 和验证命令；未实现能力继续明确标注。
2. **教程结构**：先精修 ch5，补出真正可运行的 loop 增量；再以同一事件/任务贯穿 ch6–ch8。随后把 ch9–ch12 组织成 ChangeSet → Policy → Validation → Evidence 的连续案例。
3. **章节连接**：让每章结尾直接留下下一章要解决的具体失败，不再只用统一的“系统将拥有……仍不等于……”句式。
4. **风格统一**：优先处理 ch15，其次处理 ch10、ch13、ch14、ch16 的列表化和设计文档腔；保留技术边界，不做全书短句化。
5. **局部文采**：最后才处理节奏、图示和可能的经典引用。没有可靠出处时不新增引号式名言，不为“去 AI 味”改动 ch0–ch4 的成熟句子。
