# P0 Deterministic Harness Contract

Status: Accepted contract baseline for the current P0 execution
Audience: P0 implementation agents and the integration lead
Implementation status: The repository contains an experimental Rust reference implementation of the deterministic subset; this specification remains the contract boundary and does not claim that every listed extension or fixture scenario is implemented.

This is the minimal public contract for one deterministic, end-to-end harness run. The notation is Rust-like and intentionally omits serialization-library choices. `JsonValue` means a finite JSON value with a canonical representation; the eventual implementation must select one representation without changing the field semantics.

## 1. Identity and common values

```rust
pub struct RunId(pub String);       // one execution attempt
pub struct SessionId(pub String);   // grouping identity across related attempts
pub struct EventId(pub String);     // unique within a SessionId
pub struct Sequence(pub u64);       // contiguous event order within a RunId

pub type JsonValue = /* canonical JSON value */;
```

Identity rules:

- `RunId` is unique for one invocation of the runner.
- `SessionId` is supplied by the caller and is not regenerated by a replay.
- `EventId` is unique within a session. In the deterministic P0 profile, its stable encoding is derived from `(RunId, Sequence)`; the exact string encoding remains an implementation choice.
- The first event has sequence `0`; each subsequent event increments by exactly `1`.
- IDs and sequence numbers are data, not display-only metadata.

## 2. Request, state, and limits

```rust
pub struct AgentRequest {
    pub run_id: RunId,
    pub session_id: SessionId,
    pub instruction: String,
    pub initial_context: Vec<ContextItem>,
    pub deterministic_seed: u64,
    pub limits: RunLimits,
}

pub struct ContextItem {
    pub name: String,
    pub content: String,
}

pub struct RunLimits {
    pub max_steps: u32,
    pub max_tool_calls: u32,
    pub max_context_items: u32,
}

pub enum AgentState {
    Created,
    Ready,
    AwaitingModel { step: u32 },
    ApplyingAction { step: u32 },
    PolicyChecking { call_id: String },
    ToolExecuting { call_id: String },
    RecordingResult { call_id: String },
    Validating,
    Completed,
    Failed,
    Terminated,
}
```

`AgentState` is the runner's state machine, not a model-facing status string. `Completed`, `Failed`, and `Terminated` are terminal. A run must never re-enter `AwaitingModel` after one of those states.

`max_steps` counts accepted model actions. `max_tool_calls` counts accepted calls, including calls whose tool result is a structured failure. `max_context_items` bounds context assembly; it is not permission to silently drop required input. The handling of an unrepresentable context is an unresolved integration choice noted below.

## 3. Model boundary

```rust
pub struct ModelInput {
    pub run_id: RunId,
    pub instruction: String,
    pub messages: Vec<ModelMessage>,
    pub available_tools: Vec<ToolSpec>,
    pub remaining_steps: u32,
    pub remaining_tool_calls: u32,
}

pub struct ModelMessage {
    pub role: ModelRole,
    pub content: String,
}

pub enum ModelRole {
    System,
    User,
    Tool,
}

pub struct ToolSpec {
    pub tool_id: String,
    pub description: String,
    pub input_schema: JsonValue,
}

pub enum ModelAction {
    CallTool(ToolCall),
    Finish { output: String },
}

pub struct ToolCall {
    pub call_id: String,
    pub tool_id: String,
    pub arguments: JsonValue,
}
```

The model boundary returns exactly one `ModelAction` for one `ModelInput`. `ModelAction` is structured data; free-form model text is not an action. A provider may internally use a scripted fixture, but the runner sees only this contract.

## 4. Policy and tool boundaries

```rust
pub enum PolicyDecision {
    Allow { call_id: String },
    Deny { call_id: String, reason: String },
}

pub enum ToolResultStatus {
    Succeeded,
    Failed,
}

pub struct ToolResult {
    pub call_id: String,
    pub status: ToolResultStatus,
    pub output: Option<JsonValue>,
    pub error: Option<String>,
}
```

`PolicyDecision::Deny` is a terminal run condition in this P0 slice. There is no implicit approval wait state. A tool returning `ToolResultStatus::Failed` is not automatically a harness failure: it is a structured observation returned to the model. A runtime failure that prevents a result from being constructed is an `AgentError` and terminates the run.

The contract boundary traits are:

```rust
pub trait ModelProvider {
    fn next_action(&mut self, input: ModelInput)
        -> Result<ModelAction, AgentError>;
}

pub trait ContextBuilder {
    fn build(
        &self,
        request: &AgentRequest,
        history: &[AgentEvent],
        limits: &RunLimits,
    ) -> Result<ModelInput, AgentError>;
}

pub trait PolicyEvaluator {
    fn decide(
        &self,
        call: &ToolCall,
        state: &AgentState,
    ) -> PolicyDecision;
}

pub trait ToolExecutor {
    fn execute(&mut self, call: ToolCall)
        -> Result<ToolResult, AgentError>;
}
```

The traits are extension points, not a requirement to expose every implementation through a dynamic object. The core runner must be able to use deterministic in-memory implementations without a network or API key.

## 5. Validation, evidence, outcome, and errors

```rust
pub enum ValidationStatus {
    Passed,
    Failed,
}

pub struct ValidationCheck {
    pub name: String,
    pub status: ValidationStatus,
    pub detail: String,
}

pub struct ValidationReport {
    pub status: ValidationStatus,
    pub checks: Vec<ValidationCheck>,
}

pub struct EvidenceRecord {
    pub kind: String,
    pub summary: String,
    pub supporting_events: Vec<EventId>,
    pub details: JsonValue,
}

pub enum TerminationReason {
    PolicyDenied { call_id: String, reason: String },
    BudgetExhausted,
    Cancelled,
}

pub enum RunOutcome {
    Completed {
        output: String,
        validation: ValidationReport,
    },
    Failed {
        error: AgentError,
    },
    Terminated {
        reason: TerminationReason,
    },
}

pub enum AgentError {
    InvalidRequest { detail: String },
    InvalidModelAction { detail: String },
    ModelFailure { detail: String },
    ContextFailure { detail: String },
    ToolRuntimeFailure { call_id: String, detail: String },
    ValidationFailure { detail: String },
    ReplayMismatch { detail: String },
    EventLogFailure { detail: String },
}
```

`EvidenceRecord.supporting_events` must reference events from the same run. Evidence is emitted as an event and is immutable after append. Validators may produce multiple checks, but the runner emits one final `ValidationReport` for the finish path in this P0 contract.

`AgentError` distinguishes a structured tool failure from a runtime failure. The former is a `ToolResult` with `status == Failed`; the latter prevents a valid result and yields `RunOutcome::Failed`.

The validator and event-log boundaries are:

```rust
pub trait Validator {
    fn validate(
        &self,
        request: &AgentRequest,
        events: &[AgentEvent],
    ) -> Result<ValidationReport, AgentError>;
}

pub trait EventSink {
    fn append(&mut self, event: AgentEvent)
        -> Result<(), AgentError>;
}

pub trait EventLog {
    fn read_run(
        &self,
        session_id: &SessionId,
        run_id: &RunId,
    ) -> Result<Vec<AgentEvent>, AgentError>;
}
```

For a normal run, component errors are converted into a terminal `RunOutcome::Failed` and a terminal event. An `EventLogFailure` that prevents recording the terminal event is the explicit exception and may be returned out-of-band by `run`.

## 6. Event envelope and event kinds

```rust
pub struct EventEnvelope {
    pub schema_version: u16,
    pub event_id: EventId,
    pub sequence: Sequence,
    pub run_id: RunId,
    pub session_id: SessionId,
}

pub struct AgentEvent {
    pub envelope: EventEnvelope,
    pub kind: AgentEventKind,
}

pub enum AgentEventKind {
    RunStarted { request: AgentRequest },
    ModelInputBuilt { input: ModelInput },
    ModelActionReceived { action: ModelAction },
    PolicyEvaluated { call: ToolCall, decision: PolicyDecision },
    ToolStarted { call: ToolCall },
    ToolFinished { result: ToolResult },
    ValidationCompleted { report: ValidationReport },
    EvidenceRecorded { record: EvidenceRecord },
    OutcomeRecorded { outcome: RunOutcome },
}
```

The envelope is transport-neutral. An implementation may serialize it as JSON, but it must preserve field meaning and event order. Diagnostic timestamps may be added as non-semantic metadata only; they are not part of this public payload.

The required event order for the main paths is:

```text
RunStarted
→ (ModelInputBuilt → ModelActionReceived)
→ PolicyEvaluated
→ ToolStarted
→ ToolFinished
→ (repeat model turn)
→ ValidationCompleted
→ OutcomeRecorded
```

For a finish path, the policy/tool events are absent. For a policy denial, `PolicyEvaluated` is followed by `OutcomeRecorded` and no tool events. For a provider, context, runtime, or validator error, the runner records the failure evidence when possible and then `OutcomeRecorded`.

## 7. Runner contract and termination

The minimal orchestration entry point is:

```rust
pub trait AgentRunner {
    fn run(&mut self, request: AgentRequest)
        -> Result<RunOutcome, AgentError>;
}
```

The runner must:

1. validate the request and append `RunStarted`;
2. build a `ModelInput` from the request and prior events;
3. obtain exactly one `ModelAction`;
4. apply one action, enforcing limits before side effects;
5. for `CallTool`, append policy, start, and result events in lifecycle order;
6. return to model input construction only after a structured `ToolResult` is recorded;
7. for `Finish`, run validation, append `ValidationCompleted`, then append the terminal outcome;
8. append exactly one `OutcomeRecorded` for every complete run.

There is no fall-through loop condition. The run terminates on finish, policy denial, cancellation, exhausted limits, provider/action/context/runtime failure, or failed validation. A terminal event cannot be followed by a second terminal event.

## 8. Determinism, replay, and evidence invariants

For the same request, deterministic seed, component versions/configuration, and initial event log, the harness must produce the same semantic event sequence and outcome. Semantic equality excludes diagnostic timestamps and formatting.

The following are contract invariants:

- event sequences are contiguous from `0` and scoped to a run;
- event IDs are unique within a session and stable under replay;
- event payloads are append-only and immutable;
- each `ToolCall.call_id` is unique within a run;
- `PolicyDecision::Deny` prevents `ToolStarted` and executor invocation;
- every `ToolStarted` in a complete run has one matching `ToolFinished`;
- no tool or model is invoked during replay;
- the final semantic event is `OutcomeRecorded`;
- evidence references only existing earlier events from the same run;
- a replay mismatch, duplicate call ID, invalid transition, missing result, or non-contiguous sequence is rejected with `AgentError::ReplayMismatch`;
- a complete replay reconstructs the same terminal state, validation report, evidence references, and outcome.

The P0 event log is an audit/replay contract, not yet a production recovery protocol. In particular, the contract does not claim exactly-once behavior for external side effects.

## 9. Non-goals and unresolved questions

Non-goals are defined in detail in the component-boundary document. For contract purposes, the excluded capabilities are real provider calls, live network or OS tools, streaming, parallel tool calls, hidden retries, human approval, distributed execution, durable production recovery, and Forge Studio/Godot domain types.

Unresolved questions that must not be answered implicitly by a later implementation:

1. Whether one session can contain multiple runs in P0 or only in the later recovery milestone.
2. Whether event fingerprints are required and, if so, the canonical hash algorithm.
3. Whether context overflow is a context error or a budget termination.
4. Whether a failed validation remains `RunOutcome::Failed` or becomes a separate rejected outcome.
5. Which deterministic tool fixture is the required integration fixture.

## 10. Contract freeze for later agents

Later P0 agents may implement against these fixed assumptions:

- `agent-core` owns all listed value types, the runner, state transitions, and terminal decisions.
- Components depend inward on core contracts; core does not depend on concrete adapters, tools, storage, or Forge Studio.
- A model returns exactly one `CallTool` or `Finish` action per input.
- Policy is mandatory before tool execution; deny is terminal and approval is not in P0.
- A tool lifecycle is `PolicyEvaluated → ToolStarted → ToolFinished`, with one call ID and no hidden retry.
- `RunStarted` is sequence `0`; events are contiguous, immutable, and replayable without invoking model/tools.
- Validation is required before `Completed`; all complete runs end with exactly one `OutcomeRecorded`.
- Structured tool failure is data; runtime failure is `AgentError` and ends the run.
- P0 is deterministic, in-process, side-effect-free, and does not include real integrations or Forge Studio types.
- Any deviation requires a new decision or an explicit integration review; it must not be smuggled in as an implementation detail.
