# 第 12 章：Evidence 与 Observability

**状态：设计骨架/尚未实现。** 本章定义 M7/M8 的 Evidence 引用和只读投影；P0 的 Evidence 仅是内存确定性参考。

验证器告诉我们一个检查通过了，但审查者还会问：检查何时发生？依据哪个事件？输出是什么？如果只能看最终布尔值，就无法区分真实通过、错误记录和旧结果。

## 12.1 学习目标

完成本章后，读者应能让 Evidence 引用同一 Run 的 supporting events，并解释为什么事件是事实、Summary/Trace 是视图。

## 12.2 Validation 不等于 Evidence

```text
Validation: 这个条件是否满足？
Evidence:   哪些记录支持这个判断？
```

Evidence 可以包含测试结果、diff、命令输出、结构化断言、artifact metadata，截图也可以作为概念上的 artifact，但不能因为有截图就自动证明状态正确。

```rust
struct Evidence {
    kind: String,
    summary: String,
    supporting_events: Vec<EventId>,
    details: JsonValue,
}
```

P0 的 `Evidence` 和 `EvidenceRecorded` 已经展示了这种生命周期；`observability::summarize` 是从真实事件做只读投影。它们仍不是完整 tracing、指标和 durable evidence store。

## 12.3 事件是事实，投影是视图

Runner 产生语义事件，EventLog 保存顺序，Observability 从事件生成 Summary、错误统计和 Evidence 列表。投影不应创建不存在的工具成功，也不能修改 Outcome。

```text
AgentEvent → EventLog
          ↘ Summary / Trace / Evidence projection
```

事件中应避免秘密：Authorization Header、API Key 和完整未筛选响应不得进入诊断。事件 schema 变更需要版本和迁移策略。

## 12.4 replay 与证据引用

Evidence 的 `supporting_events` 必须指向同一 Run 中已经存在的事件。重放完整日志时，应该得到相同的验证报告、证据引用和 Outcome，而不重新调用模型、工具或网络。序号缺失、重复 call id 和终态之后仍有事件，都应报告 `ReplayMismatch`。

## 12.5 验证场景

P0 demo 可断言 `event_count=11`、`evidence_count=1`；这是真实仓库中的已记录结果。更强的测试应检查拒绝路径没有工具事件、validator failure 引用了对应结果、重复运行在去除 run-specific id 后语义相同。未实现的 hash、持久化和 OpenTelemetry 集成标为 `VERIFY`。

验证场景：断言 `event_count=11`、`evidence_count=1` 的 P0 参考结果；拒绝路径没有工具事件；validator failure 引用对应结果；重放不重新调用模型、工具或网络。未实现的 hash、持久化和 OpenTelemetry 集成必须标为未完成。

## 12.6 本章将得到什么

完成 M7/M8 后，系统将拥有从事实事件到 Evidence、Summary 和 Trace 的只读投影；它仍不等于生产级指标和 durable evidence store。
