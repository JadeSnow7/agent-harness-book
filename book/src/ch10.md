# 第 10 章：ToolDescriptor、Policy 与 Approval

**状态：已实现并验证。** M6 把 provider-facing ToolDefinition 与 runtime-facing ToolDescriptor 分开；策略是内存函数，不是操作系统沙箱。

## 10.1 两种声明，两种责任

ToolDefinition 只告诉模型名称、说明和参数；ToolDescriptor 还绑定 tool id、domain、kind、input schema、output schema、source 和 version。模型看见候选能力，不因此得到权限。

ToolRegistry 在 policy 之前完成输入 schema 校验，在 handler 返回后完成输出 schema 校验。重复注册拒绝，未知工具产生结构化 error。

## 10.2 执行顺序是安全合同

本章的顺序是：

decode → input schema → EffectIntent → PolicyDecision → idempotency reserve → execute → output schema → structured result。

read 默认 allow；effect 默认 ask；显式 deny 不执行。approval 必须绑定同一个 run、call、ChangeSet、Validation 和 Evidence 摘要，任何摘要变化都会使旧批准不适用。

~~~python
descriptor = ToolDescriptor("edit", "code", EffectKind.EFFECT,
                            {"type": "object"}, {"type": "object"})
registry = ToolRegistry([ToolSpec(descriptor, lambda args: {"ok": True})])
~~~

成功路径是 read 工具通过并得到结构化结果。重要失败路径是输入 schema 错误（不触发 policy/ledger/handler）、effect 缺审批、陈旧 approval 和输出 schema 错误。路径 containment 即使存在，也不等于 OS Sandbox；本切片没有文件系统权限隔离。
