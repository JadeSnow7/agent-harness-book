# 第 16 章：完整 Harness：从通用运行时到 Forge Studio 案例

**状态：P0 参考实现 + M10 设计骨架。** P0 demo 已验证确定性组合，但真实 Provider、持久化、扩展和 Forge Studio 集成仍不在当前仓库实现范围内。

现在回看全书，Harness 不是一堆并列模块，而是一条有责任边界的执行链：

```text
Request / Session
  → Context
  → Model
  → Action
  → Policy
  → Tool Runtime
  → Observation
  → State / Events
  → Validation
  → Evidence
  → Outcome / Recovery
```

## 16.1 组合，而不是“大一统对象”

一个可解释的组装方式是让 `agent-core` 拥有状态、事件和 Runner，让其他 crate 实现边界：

```text
agent-core
├── context-engine
├── model-adapters
├── policy-engine
├── tool-runtime
├── validators
├── session-store
└── observability
```

当前仓库的 P0 demo 正是这张图的确定性垂直切片：`DeterministicRunner`、`ScriptedMockModel`、`SimpleContextBuilder`、`AllowListPolicy`、`ToolRegistry`、`RequiredOutputValidator`、`InMemoryEventStore` 组合出一个可运行闭环。它证明模块可以连起来，并不证明任何一个 subsystem 已经生产就绪。尤其是：Mock Model 不是真实 Adapter，内存 EventStore 不是 durable recovery，allowlist 不是完整 Policy Engine，Evidence projection 不是完整 Observability。

## 16.2 Forge Studio 只作为映射案例

通用核心不应依赖 Forge Studio。一个脱敏案例可以这样映射：

| 通用 Harness | 领域案例 |
|---|---|
| Tool / Capability | 场景读取、查询、修改能力 |
| Mutation | SceneOperation |
| ChangeSet | Scene ChangeSet |
| Validator | Godot headless validation |
| Evidence | 可运行证据、测试输出、artifact metadata |

这些是映射关系，不是当前仓库已经实现的 Forge Studio 集成。真正接入应在外围 adapter 中完成，领域类型不能未经抽象进入 `agent-core`。

## 16.3 一条可复核的验收路径

逐层验证比一次真实演示更可靠。当前仓库可复核的路径是：

```text
M0/M1/M2 离线测试
        ↓
Rust workspace fmt/check/test/clippy
        ↓
P0 demo：Outcome + event_count + Evidence
        ↓
mdBook：当前正文可以构建
```

本轮实际验证了前面三层和一次写入临时目录的 mdBook 构建；P0 demo 输出 `Completed`、`event_count=11`、`evidence_count=1`。这些结果证明当前确定性切片和书稿可以复核，不代表真实 Provider、网络工具、数据库恢复、并行调用、审批 UI、MCP 或 Forge Studio 集成已经完成。那些能力仍需各自的决策、实现和测试。

## 本章将得到什么

读者将得到一张可解释的 Harness 组合图、一个通用核心到领域 adapter 的映射方法，以及一份明确列出已验证能力和未实现能力的验收清单。它是架构检查点，不是生产平台完成声明。

下一阶段应从第 5 章开始，逐章把设计骨架接到真实 fixture、代码和失败路径，并保持本书与实现同步。

## 16.4 组合完成，不等于系统完成

本章前，读者已经分别看过模型、协议、工具、循环、状态、Policy、Validation 和 Evidence 的边界；本章把它们放回一条可检查的依赖方向，并说明 Forge Studio 只能作为外围领域 adapter。收益是可以用一条 P0 路径检查跨模块不变量，同时避免把领域类型倒灌进通用核心。

代价是组合会暴露单个模块没有暴露的问题：事件顺序、call id、预算、拒绝路径和验证结果必须同时一致；P0 为了确定性而省略的真实 Provider、持久化、外部副作用和并行，也不能被组合图掩盖。书籍构建本身也只能证明链接和渲染通过，不能替代运行时验收。

| 系统层 | 当前状态 |
| --- | --- |
| M0–M2 Python/Rust 教学实现 | 已实现并验证 |
| P0 确定性组合：Runner、Context、Policy、Tool、Validation、Events、Evidence | P0 参考实现，已验证 |
| M3–M10 独立增量与 Forge Studio adapter | 设计骨架/尚未实现 |
| 生产级持久化、Sandbox、扩展和运营观测 | 尚未实现 |

当前成熟度是 **Prototype**：这条组合可以作为下一轮实现的回归基线，但不具备稳定 API、真实环境安全或生产运营证据。有意留下的技术债是把 P0 保持为无网络、无外部副作用的 reference slice；后续工作应逐章补齐独立实现和失败测试，而不是继续扩大终点架构。下一步自然回到第 5 章：从真正的 Python-first Agent Loop 开始，让教学主线和 P0 组合之间的距离逐步缩短。
