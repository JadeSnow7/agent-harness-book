# 第 14 章：Planning 与 Sub-Agent

**状态：设计骨架/尚未实现。** 本章定义 M9 的计划数据、SubRun 和 delegation contract；P0 不包含 multi-agent delegation。

当任务变大，单个 loop 的上下文、预算和权限都会变得难以管理。最直接的反应是创建 Planner、Coder、Reviewer 三个角色。但角色名称本身没有解决问题：谁分配预算？子代理能看见什么？失败如何返回？

## 14.1 学习目标

完成本章后，读者应能把计划表示为任务图，把子代理表示为受限 Run，并验证隔离上下文、能力 allowlist、预算和结果证据。

## 14.2 计划首先是数据

计划可以是有依赖的任务图，而不是一段漂亮文本：

```rust
struct TaskSpec { id: String, goal: String, depends_on: Vec<String> }
struct TaskResult { task_id: String, status: Status, output: String, evidence: Vec<Evidence> }
```

Planner 只能提出计划；Runtime 决定哪些任务可运行。每个子任务应有独立 context、capability allowlist、step/token budget、取消边界和结果合同。父任务只接收必要摘要与证据，不默认共享全部历史。

## 14.3 Sub-Agent 是 Runtime abstraction

```text
Parent Run
 ├── delegate(task, capabilities, budget)
 ├── Child Run / isolated context
 └── aggregate(TaskResult) → next decision
```

子代理不是“另一个更聪明的人”，而是一次受限的 Run。它可以使用相同 Model、Tool、Policy 和 Validator 接口，但身份必须不同；事件中保留 parent_run_id。失败子运行应成为结构化结果，父运行可以重试、改计划或升级。

并行执行只有在资源互不冲突且 Policy 明确允许时才安全。默认先做串行委派；不要把并行和隐藏重试一起引入。

## 14.4 验证与聚合

测试一个子任务超预算、一个子任务被拒绝、两个子任务成功后聚合。断言父任务不会把缺少证据的 child result 当作完成。P0 不包含 multi-agent delegation；这里是设计草稿，不应引用 P0 已实现能力。

验证场景：一个子任务超预算，一个子任务被拒绝，两个子任务成功后聚合；父任务不能把缺少证据的 child result 当作完成。默认先验证串行委派，不把并行和隐藏重试一起引入。

## 14.5 本章将得到什么

完成 M9 委派部分后，系统将拥有隔离上下文、能力与预算合同，以及可验证的子运行聚合；它仍不等于成熟的多 Agent 平台。

下一章把 MCP、Skills、Hooks、Plugin 放回已有边界中解释，而不是写成生态百科。

## 14.6 委派增加的是边界数量，不是一个更聪明的角色

本章把计划表示为数据，把 Sub-Agent 表示为带身份、上下文、能力和预算的 Child Run。收益是父任务可以接收结构化 `TaskResult` 和证据，而不必把全部子对话拼回自己的上下文；子任务失败、超预算或被拒绝也能成为父任务可处理的结果。串行委派还让资源冲突和错误归因先保持可见。

代价是每个子运行都复制了一套风险：上下文可能泄露，能力 allowlist 可能配置过宽，子结果可能被父运行盲目信任，事件聚合可能丢失 parent/child 关系。并行一旦加入，还会出现写入冲突、取消传播和预算竞赛。AI 的错误可以跨层放大：父模型相信一个没有 Evidence 的 child result，就会把局部幻觉升级成全局完成声明。

| 能力 | 当前状态 |
| --- | --- |
| P0 单一 DeterministicRunner 与事件隔离 | P0 参考实现，不含 delegation |
| `SubRun`、delegation contract、串行聚合测试 | 设计骨架/尚未实现 |
| 并行执行、跨子任务事务、成熟多 Agent 调度 | 尚未实现 |

当前成熟度是 **Experimental**：接口方向和验证场景已经冻结，但仓库没有 multi-agent 代码证据。有意留下的技术债是先不引入并行和隐藏重试，优先验证隔离、预算和证据完整性。下一章面对的是更开放的能力来源：外部 Tool、Skill、Hook 和 Plugin 如何接入而不绕过已有的 Policy、Runtime 和生命周期。
