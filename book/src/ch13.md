# 第 13 章：Stop Conditions、Progress 与 Loop Engineering

**状态：设计骨架/尚未实现。** 本章定义 M9 的 Progress、StopPolicy 和升级路径；当前没有通用停滞检测实现。

有了状态、验证和事件，`while true` 仍然不够。模型可能反复读取同一文件、重复提出失败调用，或者不断生成“再试一次”。系统需要判断是否有进展，并在预算、停滞、风险和人工升级之间做选择。

## 13.1 学习目标

完成 M9 后，读者应能区分 Completed、BudgetExhausted、Stalled 和 Escalate，并为具体任务定义可验证的 progress oracle。

## 13.2 停止不是一个布尔值

```rust
enum StopDecision {
    Continue,
    Completed,
    BudgetExhausted,
    Stalled { fingerprint: String },
    Escalate { reason: String },
}
```

基本停止条件包括：验证通过、步骤/工具/token/成本预算耗尽、取消、policy denial、重复动作阈值、连续验证失败和上下文无法构造。停止原因必须进入 Outcome，而非只打印一行日志。

## 13.3 什么叫进展

进展不是模型输出更长。可以观察目标状态差异、验证通过项增加、错误减少、ChangeSet 缩小或新证据出现。不同任务需要不同 progress oracle；没有 oracle 时宁愿使用保守预算，也不要声称通用停滞检测已经解决。

```text
state_before + action + observation → state_after
progress = measure(state_after) - measure(state_before)
```

动作 fingerprint 可以帮助识别完全重复，但相同动作有时确实需要重试，所以 fingerprint 只应触发策略，不应直接等同失败。

## 13.4 代码增量与验证

用 P0 的三次可达调用加第四次不可达脚本测试步数边界；用重复工具 fixture 测停滞；用验证失败后进展的 fixture 测“失败不等于无进展”。运行结果要区分 `BudgetExhausted`、`Stalled` 与 `PolicyDenied`。

计划中的 Harness：

```text
State + Validation + Evidence
              ↓
       StopPolicy / Progress
              ↓
 Continue | Complete | Stop | Escalate
```

验证场景：使用三次可达调用和第四次不可达脚本测试预算；重复工具 fixture 测停滞；验证失败后有新证据的 fixture 测“失败不等于无进展”。运行结果必须区分 `BudgetExhausted`、`Stalled` 与 `PolicyDenied`。
