# 第 11 章：Validation：模型说完成不等于完成

**状态：设计骨架/尚未实现。** 本章定义 M7 Validator 和 ValidationReport；P0 的 `RequiredOutputValidator` 只用于证明验证阶段存在。

假设模型最后回答：“代码已经修复。”这只是一个声明。Harness 必须在环境里执行可重复的检查：测试、schema 断言、文件存在性、构建或领域检查。只有检查通过，才允许进入 `Completed`。

## 11.1 学习目标

完成本章后，读者应能把模型声明与环境事实分开，设计可重复的检查，并让验证失败进入结构化结果而不是被改写成成功。

## 11.2 Final answer 是声明

```text
Agent: “已修复。”
Harness: cargo test
Result: FAILED
```

因此 Loop 的 Finish 分支应是：

```rust
ModelAction::Finish { output } => {
    let report = validator.validate(&events)?;
    if report.passed() { Completed(output, report) }
    else { Failed(report) }
}
```

`RequiredOutputValidator` 只检查输出中是否包含必要文本，是 P0 的最小确定性验证器，不是完整 Validation 系统。它帮助我们验证“验证阶段存在”，而不是证明真实代码正确。

## 11.3 验证器要回答什么

一个好的 validator 说明输入、检查和失败详情：命令是什么、退出码是多少、检查了哪个 artifact、结果是否可重复。模型生成的解释不能替代退出码。命令执行也必须受 Policy 和 Sandbox 约束。

Validation 与 Tool Runtime 的职责不同：工具产生观察，validator 判断目标条件。Validation 也与 Evidence 不同：前者做判断，后者记录支持判断的材料。

## 11.4 失败后的选择

验证失败不一定意味着整个系统崩溃。可以把报告作为下一轮观察，让模型修复；也可以达到预算后终止；高风险任务可以升级人工。无论如何，不能将失败报告改写为成功文本。

## 11.5 验证场景

用一个总是失败的 Fake Validator，断言不会产生 Completed；用通过和失败的两组 fixtures，断言报告包含每个 check；验证事件包含失败原因，并且重放不会再次运行真实命令。P0 fixtures 的 `validator_failure` 体现了“工具成功但目标不满足”的独立路径。

验证场景：用总是失败的 Fake Validator 断言不会产生 Completed；通过和失败 fixtures 都要包含每个 check；重放时不能再次运行真实命令。P0 的 `validator_failure` 只作为事实验证路径的参考。
