# 常见 Agent 产品的 Harness 路线

下面这些工具并不属于完全相同的类别，但它们代表了几种常见的 Harness 产品路线。

Codex：任务执行型路线

Codex 类产品更强调把一个相对完整的开发任务交给 Agent，由 Agent自行读取仓库、修改代码、执行命令并验证结果。

其 Harness 重点通常包括：

任务级执行；

仓库上下文读取；

命令执行环境；

权限与沙箱；

文件修改；

测试和结果验证；

长任务状态管理。

这种路线试图让用户关注“需要完成什么”，而不是持续关注每一次代码编辑。

Claude Code：终端与工程工作流路线

Claude Code 采用终端作为主要交互入口，强调 Agent 对现有代码仓库和开发工具链的直接操作。

其 Harness 路线更关注：

项目级上下文；

文件和终端工具；

工程指令；

权限确认；

开发工作流扩展；

Agent 行为定制；

与现有命令行工具配合。

这种设计适合希望 Agent 深度参与真实工程流程的开发者。

Cursor：IDE 原生路线

Cursor 将 Agent 能力嵌入代码编辑器。

其 Harness 与编辑器状态深度结合，可以直接获得：

当前打开的文件；

光标位置；

代码选区；

编辑器诊断；

项目索引；

代码差异；

用户的实时编辑行为。

这种路线强调人和 Agent 在同一个编辑环境中协作，由用户持续观察和调整 Agent 的修改。

OpenCode：开放与多模型路线

OpenCode 一类开源 Coding Agent 更强调开放实现、模型可替换和终端工作流。

其价值通常不只是提供一个现成工具，也在于让开发者能够研究和修改：

模型适配层；

工具系统；

会话状态；

Agent Loop；

权限机制；

上下文策略；

用户界面。

这种路线适合作为理解 Agent Harness 实现方式的工程参考。

Pi：极简与可组合路线

Pi 所代表的是一种更加克制的设计思路：Harness 不一定需要内置大量功能，而可以只保留稳定、清晰的核心抽象。

其重点通常不是提供最多的开箱即用功能，而是：

保持 Agent Loop 简单；

让模型、工具和上下文可以替换；

避免过早引入复杂抽象；

将定制能力交给开发者；

通过组合而不是堆叠功能构建系统。

这种路线尤其适合作为“从零理解和实现 Harness”的参考，因为它更容易暴露 Agent 系统真正不可缺少的部分。

1.7 本书所说的 Harness

本书不会尝试复刻某一个现有产品，也不会把 Harness 理解为某个固定框架。

本书所构建的 Harness，是一个能够支持以下闭环的最小 Agent 运行系统：

理解目标
   ↓
构建上下文
   ↓
模型决策
   ↓
调用工具
   ↓
修改环境
   ↓
验证结果
   ↓
失败恢复或继续执行

在后续章节中，我们将逐步实现：

模型适配层；

Tool Registry 与 Tool Runtime；

Context Engine；

Session 与 State；

Permission 与 Policy；

Agent Loop；

Validation；

Observability；

Recovery。

最终，模型不再只是回答一个问题，而是在 Harness 的约束下，持续完成一个可以被检查和验证的任务。

本章小结

大语言模型提供了推理能力，但 Harness 决定了这种能力如何进入真实环境。

一个可靠的 Agent，不仅要能够生成正确的下一步，还需要：

获取正确的上下文；

调用正确的工具；

在允许的范围内行动；

记录执行状态；

验证实际结果；

在失败后恢复；

在满足条件时停止。

因此，在构建 Agent 时，一个更重要的问题往往不是：

应该选择哪个模型？

而是：

应该为模型提供一个怎样的 Harness？
