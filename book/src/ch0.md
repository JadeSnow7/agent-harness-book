# 绪论：从模型到 Agent 系统

或许你听过一句话：在 AI 时代，如果你学东西足够慢，那就不用学了。

自 LLM 走进大众视野以来， Prompt Engineering、Context Engineering、Harness Engineering 和 Loop Engineering 等一个个工程概念层出不穷，这使得个人在学习 AI 时往往陷入迷茫和焦虑。笔者写这个系列的初衷正是记录自己的学习路径，并分享尽可能闭环和简明的工程实践经验，希望能帮助到同样在学习 Agent 的你。

本书的目标不是一味追新或者陈述概念，而是从真实的工程实践中逐步理解 Agent Harness。

## 0.1 大模型不是 Agent

理解 Agent 的第一步，是把模型能力与系统能力分开：

- `LLM != Agent`
- `Agent System = Model + Harness + Environment`

模型根据输入生成文本或结构化动作。它可以提出“读取文件”“执行测试”或“发送请求”，但模型本身不拥有文件权限，也不会自动执行这些动作。负责上下文、权限、工具、状态、验证和停止条件的是模型外部的程序。

在本书的定义里，**Harness 是连接模型与环境的运行支撑层**。它构造上下文，将模型提出的动作交给受控工具，记录环境返回的观察，再决定是否继续下一轮。

```text
用户目标
   ↓
Harness 构造上下文 → Model 提出动作
   ↑                     ↓
状态与验证结果 ← Environment 执行动作
```

这个关系式是工程上的简化，不是对所有智能体研究的统一定义。它的价值在于划清责任：模型负责生成决策候选，Harness 负责让决策在明确的边界内落地。

## 0.2 为什么从 Harness 开始

当 Agent 在真实环境中失败时，问题未必来自提示词：

- 必要文件没有进入上下文；
- 模型提出了不存在的工具或无效参数；
- 工具超时，却没有形成下一轮可以观察的错误；
- 系统声称任务完成，却没有检查环境状态；
- 循环反复执行同一种失败动作，没有预算和停止条件。

继续润色提示词可能缓解其中一部分问题，却不能替代工具协议、权限系统、事件记录和验证器。可靠性来自模型与 Harness 的共同设计。

## 0.3 本书路线

本书分为五个 Part：

1. **从模型开始**：建立 Model、Harness、Environment 的共同语言，完成一次模型调用、统一协议和一次工具闭环。
2. **让系统循环行动**：引入有界 Loop、Context、Session 和 Recovery。
3. **让行动受到约束**：把副作用、变更审查、Policy、Sandbox、Validation 和 Evidence 分开。
4. **让循环可靠地收敛**：讨论 Progress、Stop Policy、Planning 和 Sub-Agent。
5. **扩展 Harness**：解释 MCP、Skills、Hooks、Plugin，以及通用 Harness 到 Forge Studio 的映射。

第 2–4 章围绕一个小任务逐步升级：模型先尝试回答如何读取 `hello.txt`，然后学习用统一协议表示 `read` 候选，最后由 Runtime 执行读取并返回观察。后续章节继续追问循环、上下文、恢复、验证和停止。

## 0.5 方法论：如何更可靠地使用 AI

前文讨论的是怎样让模型在一个可验证的边界内工作。现在把同一套思想用在我们自己的工作流上：**把 AI 当作 Model，把自己与测试、版本控制和执行环境组织成 Harness**。

这里所说的“更可靠”，针对的是软件开发，以及其他需要外部执行、事实核验和明确验收的复杂任务。它不是聊天、写作或所有日常场景的唯一方法。对这类复杂任务而言，关键不在于找到一句完美的 prompt，也不在于把整个项目交给模型自行完成，而在于把 AI 纳入一个有目标、有边界、有执行记录、有外部验证和停止条件的工作流。

AI 负责提出候选，人和工具链负责决定候选能否执行、结果是否可信，以及任务是否真的完成。模型能力影响候选的质量与上限，却不会消除 Harness 的职责。这里的类比也有边界：人的谨慎不能替代真正的 Policy、Sandbox、Runtime 或 Validator，人工 review 更不能凭一句“看起来没问题”充当可重复的验证。

这套工作方式可以分成五个阶段：

| 阶段 | Harness 职责 | 本书落点 |
| --- | --- | --- |
| 定义完成条件 | 写清目标、输入、输出、风险与验收判据 | ch1、ch2.3、ch11 |
| 构造上下文与边界 | 提供必要事实，限定范围、工具与禁止动作 | ch2、ch6、ch10 |
| 产生并受控执行增量 | 让候选经过权限判断，再由 Runtime 执行 | ch3、ch4、ch10 |
| 验证并保存证据 | 用环境状态和可重复检查判断结果 | ch2.5、ch11、ch12 |
| Review 并决定下一轮 | 接受、修正、回退、升级或停止 | ch5、ch13 |

其中 ch2–ch4 已经提供可以运行的教学实践；ch5、ch6、ch10–ch13 目前仍包含设计骨架。上表说明概念将在哪里展开，不表示后续 milestone 已经实现。

```text
定义目标与验收条件
        ↓
构造上下文、权限与任务边界
        ↓
AI 提出候选
        ↓
Policy 判断 → Runtime 受控执行
        ↓
环境返回 Observation
        ↓
Validation 产生 Evidence
        ↓
满足验收条件？
  否 → 修正原型、上下文或执行方案
  是 → Review 并结束
```

**第一步：先定义完成条件，而不是先向 AI 提问。** 写清任务目标、输入、输出、责任人、风险和验收判据。面对尚不清楚的问题，可以先做一个最小原型来暴露未知；原型是一种探索手段，不是所有任务的强制起点。最重要的问题是：如果 AI 给出一个看起来合理的结果，你凭什么判断它已经完成？如果没有答案，后面的 prompt 再精巧，也只是在加速一个没有终点的过程。

**第二步：构造上下文、任务与边界，而不只是润色 prompt。** 模型请求不只有措辞，还包括必要事实、当前状态、允许修改的范围、可用工具、禁止动作和输出契约。模型可以利用训练中获得的知识、当前输入和工具返回的观察，却不能凭空知道未进入上下文的环境事实。第 2 章里的模型看不到 `hello.txt`，所以它不能证明文件内容；问题不在于那句话写得不够漂亮，而在于工作流没有提供读取能力。此时应该问：AI 是否获得了完成本轮任务所需的事实，以及足够明确的权限边界？

**第三步：让 AI 产生并执行一个可审查的增量。** AI 可以提出方案、生成代码或调用工具，但动作应先经过权限判断，再在受控环境中执行。每轮增量要小到足以看清 diff、运行结果和失败原因，也要完整到能够验证一项真实变化。此时要问的不是“它写了多少”，而是：本轮允许它改什么，实际执行了什么，又明确禁止了什么？

**第四步：用外部证据验证，而不是让 AI 自证正确。** 测试、lint、类型检查、diff、退出码和环境状态可以产生可复现的证据；AI 可以帮助运行、解释和修复这些检查，但“我已经完成”不是完成证明。审核强度还应与风险相称：低风险、可逆且有自动化检查的操作可以更多交给系统，高风险或难以恢复的操作则需要更严格的审批与人工验收。最终要回答的是：哪条独立证据证明结果满足了第一步的验收判据？

**第五步：通过项目 review 决定继续、回退或停止。** 把大任务拆成有验收判据的里程碑，根据目标差异、验证结果、风险和预算，选择接受、修正、回退、升级或结束。模型可以建议停止，但它的声明不能单独证明任务已经收敛；停止决定必须建立在验收条件和可观察状态上。每一轮结束时都应能回答：为什么现在应该继续，或者为什么已经可以停止？

失败会沿着这条链路回流：证据不足，可能需要补验证；执行越界，应该收紧 Policy；结果偏离目标，可能要修正上下文；若连完成条件都无法判断，就要回到任务定义。循环不是为了让 AI 多试几次，而是让每一次尝试都留下可供下一轮使用的观察。

衡量 AI 使用得好不好，不看 prompt 写得多漂亮，也不看它一次生成了多少代码，而看你能否回答四个问题：**它依据什么、改变了什么、如何验证、为什么可以停止。** 回答不出来，工作流就还没有闭环。

## 0.6 本章小结

模型提供生成和推理能力，Harness 决定这种能力如何进入真实环境。后面的学习顺序是：

```text
模型调用 → 统一协议 → 工具候选 → 一步闭环
→ 循环 → 上下文 → 状态与恢复 → 权限与验证
→ 证据 → 收敛 → 委派与扩展
```

下一页的阅读指南会说明需要什么基础、为什么正文使用 Python 主线，以及哪些章节目前仍是设计骨架。

## 0.7 先给系统拍一张起点照片

这一章没有新增可执行模块。它做的是把问题空间和验收语言先固定下来，否则后面的代码很容易变成一串彼此独立的技巧。以当前仓库为准，读者从下面这个状态进入本书：

| 能力 | 起点状态 |
| --- | --- |
| 一次模型调用、统一协议、一步 Tool Runtime | 已实现并验证，主线为 Python；有 Rust 对照 |
| 多轮 Agent Loop、Context、Session、Validation、Evidence | 有 P0 组合参考；对应独立章节实现尚未全部提供 |
| durable recovery、ChangeSet、生产级 Sandbox、Sub-Agent、MCP/Plugin | 设计骨架/尚未实现 |

这张照片带来一个很实际的收益：读者可以区分“本章正在构建的能力”和“为了说明终点而提前画出的架构”。代价是路线不会假装完整；有些章节只能先冻结问题和测试合同，不能提供一个可直接复制到生产环境的 subsystem。这是有意留下的技术债，因为如果一开始把持久化、审批、沙箱和多代理全部塞进来，读者反而看不清第一条模型—环境闭环是怎样形成的。

当前这一层属于 **Experimental**。不是因为模型调用一定不可靠，而是全书的系统边界、公共 API 和后续里程碑仍在演进。它已经足以支持教学和离线实验，却没有足够证据支持稳定性或生产承诺。

下一章因此不能继续罗列模型能力，而要先回答一个更窄的问题：当模型、Harness 和 Environment 被放在同一张图上时，究竟谁负责什么，失败应由谁判定？这就是 Harness 职责边界产生的原因。
