# 绪论：从模型到 Agent 系统

或许你听过一句话：在 AI 时代，如果你学东西足够慢，那就不用学了。

自 LLM 走进大众视野以来，Prompt Engineering、Context Engineering、Harness Engineering 和 Loop Engineering 一个个出现。概念越来越多，反而容易让初学者忘记一个朴素的问题：模型究竟改变了什么，程序又负责了什么？

本书不从"如何写出一句神奇的提示词"开始。我们从一个更容易复查的系统开始：模型提出候选，Harness 组织候选进入运行时，环境返回事实，验证器和人共同判断下一步。之后每一章只增加一项能够观察、运行和验证的能力。

这些术语和后面陆续出现的新名词，你现在都不需要立刻记住或完全理解——它们会随着章节推进逐一展开、逐一落地成代码。本书是一本工程实践手册，目标是带你把系统一步步搭起来、跑起来；暂时没完全理解某个概念，不会妨碍你跟着代码继续往下走。

## 0.1 模型不等于 Agent

先看一个具体动作。模型可以回答："请读取 `hello.txt`，然后告诉我文件内容。"这句话听起来像完成了任务，实际上什么也还没有读取。模型生成的是文本，或者一个候选动作；文件是否存在、进程是否有权限、路径是否越界，都要由外部系统检查。

因此，本书先使用一个足够工作的关系式：

```text
Agent System = Model + Harness + Environment
```

这里的三个词不是把所有 Agent 研究一网打尽的定义，而是本书的观察入口。Model 产生文本或候选动作；Harness 负责把目标、上下文、策略、工具、状态和验证组织起来；Environment 才拥有文件、进程、网络和权限这些真实资源。详细的责任边界留到 ch1，本章只先把位置摆对。

模型输出不是环境事实。它可以说"测试通过"，却不能凭这句话让测试真的通过。只有环境状态、退出码、测试结果、事件记录和其他可复查材料，才能支持验收结论。

### 第一次遇到的几个基础词

这里的网络知识只需要一层：模型 API 本质上是客户端向远程服务发送请求，再接收响应。请求和响应是数据，不是模型获得本机权限的通行证。文件、进程、网络和权限由操作系统及运行时控制，模型本身没有这些权限。

本书还会反复使用五类数据：

- **Input**：交给模型的数据，例如目标、上下文和工具说明；
- **Candidate Action**：模型建议执行的动作，例如 `read("hello.txt")`；
- **Observation**：动作进入环境后返回的事实，例如文件内容或错误；
- **Event**：系统保存的过程记录，例如一次调用、一次拒绝或一次验证；
- **Evidence**：支持验收结论的可复查材料，例如测试输出、状态检查和事件引用。

这不是在 ch0 展开 HTTP、进程模型、序列化或事件溯源教程。现在只要记住：建议、执行结果、过程记录和验收材料不能混成一类。

闭环从 User Goal 开始。Harness 根据目标构造 Context，把 Input 交给 Model。Model 只提出文本或 Candidate Action，不直接触碰 Environment。Candidate Action 先经过 Policy：允许的动作才进入 Runtime，Runtime 再以受控方式接触环境。Environment 返回 Observation，Harness 保存 State / Events，并让 Validation 根据环境状态形成 Evidence。最后，人根据目标、证据、风险和预算决定继续或停止。

这条链路解决的是一个很具体的问题：如果模型说"已经完成"，我们知道该去哪里找反证，也知道什么材料可以支持"确实完成"。如果动作被拒绝，拒绝发生在执行之前，而不是执行后才从日志里猜测。

图中绿色部分是仓库已有的 M0–M2 证据链：一次模型调用、统一协议和一步工具 Runtime；蓝色部分是已实现并验证的 Python M3–M10 教学链。黄色部分仍是 P0 的确定性组合参考，灰色虚线只保留 Rust M3–M10 与生产能力路线。颜色只表示证据状态，不表示任何部分已经生产可用。

## 0.3 为什么先从 Harness 入手

当 Agent 在真实环境中失败时，问题未必来自提示词：必要文件可能没有进入上下文，模型可能提出不存在的工具，工具可能超时却没有留下下一轮能理解的错误，系统也可能在没有检查环境状态时宣布完成。

继续润色提示词有时有用，却不能替代工具协议、权限判断、状态记录、验证和停止条件。Harness 这个词的价值，不在于再造一个漂亮名词，而在于提醒我们：模型能力必须经过一层可观察、可限制、可验证的程序，才能成为系统行为。

本章不详细规定这层程序的公共接口，因为那会把 ch1 的问题提前回答。我们只先保留一个判断：模型负责提出候选，系统负责决定候选能否落地，环境负责产生事实。

## 0.4 同一个工程怎样逐章获得能力

本书不是把若干 Demo 拼成目录，而是围绕同一个小任务逐步增加能力。读者先看到模型如何回答，再看到 Provider JSON 如何被隔离，接着让一个 `read` 候选经过 Runtime 获得 Observation；之后才引入循环、上下文预算、状态、恢复、变更、Policy、Validation、Evidence 和停止。

路线可以压缩成：

```text
模型调用 → 统一协议 → 工具候选 → 一步闭环
→ 循环 → 上下文 → 状态与恢复 → 权限与验证
→ 证据 → 收敛 → 委派与扩展
```

仓库中的 M0–M2 示例、Python M3–M10 切片和 P0 参考切片是这条路线的现有证据，但不是本轮 ch0 重组的新实现。P0 是确定性、内存内、无外部副作用的组合参考；Python M4–M10 的状态以累计包、独立测试和实现索引为准。

全书五个 Part 的问题顺序如下：

1. **从模型开始**：共同语言、一次调用、统一协议和一步闭环；
2. **让系统循环行动**：有界 Loop、Context、Session 和 Recovery；
3. **让行动受到约束**：副作用、ChangeSet、Policy、Sandbox、Validation 和 Evidence；
4. **让循环可靠地收敛**：Progress、Stop Policy、Planning 和 Sub-Agent；
5. **扩展 Harness**：MCP、Skills、Hooks、Plugin，以及通用 Harness 到 Forge Studio 的映射。

这是一张路线图，不是完成清单。ch0 只交付架构和工作流程资产；本轮没有开始 ch2 及之后的逐章真实实现，也没有新增 Agent Runtime 能力。

## 0.5 如何用 AI Coding 完成本项目

前面的闭环也适用于写这本书和维护这份代码：可以把 AI 当作 Model，把作者、仓库、测试、文档构建和版本控制组织成一个更大的 Harness。AI 可以起草方案和修改，但它不能仅凭自己的完成声明证明章节或代码已经正确——这条原则和后面每一章要讲的"模型输出不是环境事实"完全一致。

### Prompt 与 Workflow 的基本技巧

一次可靠的增量通常遵循这几步：

1. **先只读检查**：让 AI 先看当前目录、`git status`、相关决策记录和已有实现，避免覆盖作者未提交的修改；
2. **定义目标和验收条件**：说清楚这一步要交付什么、用什么命令验证、不允许碰哪些文件；
3. **先出 Prompt，再动手**：由 AI 起草一份范围明确的实施 Prompt，人工批准后才允许写文件；未批准，就退回 Prompt 阶段，而不是直接改代码；
4. **只做最小增量**：批准后只实施这一步范围内的修改，避免顺手扩大范围；
5. **跑验证、留证据**：运行测试、lint、类型检查或文档构建，保存退出码和 diff，作为可复查的材料；
6. **人工 Review 不可省略**：AI 的"已经完成"通向的是 Review，不是任务完成，人可以接受、修正或回退。

### 跟进开发的技巧：状态记录与汇报

AI 协作写作最容易出的问题，不是写错代码，而是让人搞不清楚"现在到底做到哪一步了"。几条实践经验：

- **给每项能力挂一个状态标签**：本书统一用三档——已实现并验证、P0/参考实现、设计骨架/尚未实现。写状态之前先跑一遍验证命令，不要凭记忆写状态；
- **每次增量结束都用同一组命令复现结果**，把命令和输出放进完成报告，而不是只写一句"已经完成"；
- **明确写下这次有意留下的技术债**，以及它会在哪一步被处理；技术债不写清楚，容易被下一次增量默认为"已经解决"；
- **版本化你的 Prompt**：批准并执行过的 Prompt 不要事后悄悄改写；范围变化就新建一版，带上触发这次变化的证据。

这套记录习惯本身就是全书反复出现的 Evidence / Observability 思路的一次具体应用：状态标签是投影，验证命令的输出才是事实源。当前仓库的实际进度以[实现索引](implementations.md)和[阅读指南](reading-guide.md)里的章节状态说明为准，这里不重复列出一份会很快过期的状态表。

## 0.6 本章限制，以及下一章的问题

这张地图不是完整的架构规范，也不是生产级 Sandbox、Recovery、Validation 或 Observability 的证明。它只固定读者接下来需要使用的语言：输入不等于动作，动作不等于执行，观察不等于证据，证据也必须回到目标和验收条件中解释。

因此，本章只能声明：**ch0 架构与工作流程资产已建立，mdBook 构建已验证；没有新增 Agent Runtime 能力。** 本节是路线快照：ch1 已补齐 Model/Harness 边界，ch2–ch5 与 Python M4–M10 已分别有可离线验证入口；Rust 累计工程仍不包含 M3–M10。本章不把文档构建等同于运行时代码正确，也不把 P0 参考切片写成生产能力；读者应以实现索引和当前源码、测试为准。

下一章要回答的问题更窄，也更难：当 Model、Harness 和 Environment 放在同一张图上时，究竟谁负责什么，失败应由谁判定？只有边界先说清楚，后面的代码才不会把责任藏在一条过长的调用链里。
