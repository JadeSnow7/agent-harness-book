# 绪论：从模型到 Agent 系统

如果你已经听过 Prompt Engineering、Context Engineering、Harness Engineering 和 Loop Engineering，却仍然不知道应该从哪里开始，这本书提供一条可运行的学习路径：先调用模型，再把模型输出变成候选动作，最后让动作在明确边界内执行、验证并停止。

本书的目标不是追逐新名词，而是让你亲手看见可靠性如何在模型外围被设计出来。

## 0.1 大模型不是 Agent

理解 Agent 的第一步，是把模型能力与系统能力分开：

- `LLM != Agent`
- `Agent System = Model + Harness + Environment`

模型根据输入生成文本或结构化动作。它可以提出“读取文件”“执行测试”或“发送请求”，但模型本身不拥有文件权限，也不会自动执行这些动作。负责上下文、权限、工具、状态、验证和停止条件的是模型外部的程序。

在本书的定义里，**Harness 是连接模型与环境的运行支撑层**。它构造上下文，将模型提出的动作交给受控工具，记录环境返回的观察，再决定是否继续下一轮。

```text
用户目标
   ↓
Harness 构造上下文 → Model 提出动作
   ↑                     ↓
状态与验证结果 ← Environment 执行动作
```

这个关系式是工程上的简化，不是对所有智能体研究的统一定义。它的价值在于划清责任：模型负责生成决策候选，Harness 负责让决策在明确的边界内落地。

## 0.2 为什么从 Harness 开始

当 Agent 在真实环境中失败时，问题未必来自提示词：

- 必要文件没有进入上下文；
- 模型提出了不存在的工具或无效参数；
- 工具超时，却没有形成下一轮可以观察的错误；
- 系统声称任务完成，却没有检查环境状态；
- 循环反复执行同一种失败动作，没有预算和停止条件。

继续润色提示词可能缓解其中一部分问题，却不能替代工具协议、权限系统、事件记录和验证器。可靠性来自模型与 Harness 的共同设计。

## 0.3 本书路线

本书分为五个 Part：

1. **从模型开始**：建立 Model、Harness、Environment 的共同语言，完成一次模型调用、统一协议和一次工具闭环。
2. **让系统循环行动**：引入有界 Loop、Context、Session 和 Recovery。
3. **让行动受到约束**：把副作用、变更审查、Policy、Sandbox、Validation 和 Evidence 分开。
4. **让循环可靠地收敛**：讨论 Progress、Stop Policy、Planning 和 Sub-Agent。
5. **扩展 Harness**：解释 MCP、Skills、Hooks、Plugin，以及通用 Harness 到 Forge Studio 的映射。

第 2–4 章围绕一个小任务逐步升级：模型先尝试回答如何读取 `hello.txt`，然后学习用统一协议表示 `read` 候选，最后由 Runtime 执行读取并返回观察。后续章节继续追问循环、上下文、恢复、验证和停止。

## 0.4 背景侧栏：关注点逐层外移

下面的时间线只是观察框架，不是公认的历史分期，也不表示后一个阶段会取代前一个阶段。相关行业文章与产品能力具有时效性，发布前应重新核验来源和日期。

| 关注点 | 主要问题 | 本书对应内容 |
|---|---|---|
| Prompt Engineering | 怎样组织一次模型输入 | ch2 的请求和提示 |
| Context Engineering | 本轮应该放什么、删什么 | ch6 |
| Harness Engineering | 模型如何获得状态、工具、权限和反馈 | ch1、ch3–ch12 |
| Loop Engineering | 系统如何行动、纠错、收敛并停止 | ch5、ch13–ch14 |

这些方向不是四代互相替代的技术，而是工程边界逐层扩大：上下文管理仍然需要提示，Harness 仍然需要上下文，Loop 仍然需要工具与验证。

## 0.5 本章小结

模型提供生成和推理能力，Harness 决定这种能力如何进入真实环境。后面的学习顺序是：

```text
模型调用 → 统一协议 → 工具候选 → 一步闭环
→ 循环 → 上下文 → 状态与恢复 → 权限与验证
→ 证据 → 收敛 → 委派与扩展
```
